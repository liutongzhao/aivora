# Aivora 正式产品化设计规格

**日期：** 2026-09-24  
**状态：** 待审阅  
**适用分支：** `main`

## 1. 目标

将当前 Aivora 的基础 Web 骨架和旧远程连接逻辑升级为可实际使用的本地产品：

1. Web 页面具备正式产品的视觉质量、信息架构和交互状态。
2. Electron 桌面客户端、Web 管理端和 Python 后端全部连接到本地服务。
3. 真实跑通“截图 → 上传 → MinIO → AI Worker → OpenAI 兼容模型 → Redis Streams → SSE → 桌面端答案”的完整闭环。
4. 为不同题型建立独立、详细、可维护的提示词模板。
5. 使用自动化测试和真实本地服务验证功能，而不是只验证页面能够打开。

## 2. 范围

### 2.1 本次包含

- Electron 本地 API、Web 和 Socket.IO 地址配置。
- Web 登录、注册、工作台、任务、历史、模型设置、远程控制和管理后台。
- Aivora 统一视觉系统。
- AI 题型提示词注册和版本化管理。
- AI 输出解析、原始输出保存和解析警告。
- 任务状态、流式事件和失败状态的完整展示。
- 后端、Worker、MinIO、Redis Streams、SSE 和桌面客户端联调。
- 截图到答案的端到端测试。

### 2.2 本次不包含

- 积分、计费、订单和支付。
- 邀请、增长和推广体系。
- 多管理员权限层级。
- 面向公网的多租户计费隔离。
- 重写现有 Electron 截图和快捷键底层实现。

## 3. 产品定位和设计原则

Aivora 是一个本地优先的 AI 工作台，用户通过桌面客户端采集内容，通过 Web 页面管理任务、模型和设备。

设计原则：

- **克制：** 使用中性颜色、清晰层级和适量留白，避免夸张渐变和泛化的 AI 装饰。
- **可解释：** 任务状态、处理阶段、模型和错误原因必须明确可见。
- **高密度但不拥挤：** 让用户能快速查看任务、答案和设备状态。
- **一致：** 登录页、用户端、管理端和远程控制使用同一套颜色、间距、控件和状态表达。
- **本地优先：** 开发环境默认访问本机 API，不依赖旧远程域名。

## 4. 总体架构

系统保持模块化单体 API + Worker + Web + Electron 的结构：

```text
Electron Desktop
  ├── REST /api
  ├── SSE /api/ai/stream
  └── Socket.IO /remote
              │
              ▼
FastAPI API
  ├── Identity
  ├── Settings
  ├── Models
  ├── Tasks
  ├── Files
  ├── Devices
  └── Admin
       ├── PostgreSQL
       ├── MinIO
       └── Redis
              │
              ▼
Celery Worker
  ├── MinIO 读取截图
  ├── Prompt Registry
  ├── OpenAI Compatible Provider
  └── Redis Streams 任务事件

Web Management
  ├── REST /api
  └── Socket.IO /remote
```

本地开发服务：

| 服务 | 地址或端口 | screen |
|---|---|---|
| Electron + Vite | `http://127.0.0.1:54321` | `aivora-dev` |
| Next.js Web | `http://127.0.0.1:3000` | `aivora-web` |
| FastAPI API | `http://127.0.0.1:18000` | `aivora-backend` |
| Celery Worker | 无 HTTP 端口 | `aivora-worker` |
| PostgreSQL | `127.0.0.1:15439` | Docker |
| Redis | `127.0.0.1:16379` | Docker |
| MinIO API | `127.0.0.1:19000` | Docker |
| MinIO Console | `127.0.0.1:19001` | Docker |

## 5. 本地连接配置

开发配置统一使用：

```json
{
  "api": {
    "baseUrl": "http://127.0.0.1:18000",
    "aiEndpoint": "/api/ai",
    "webEndpoint": "/api"
  },
  "websocket": {
    "url": "http://127.0.0.1:18000"
  },
  "web": {
    "baseUrl": "http://127.0.0.1:3000",
    "logoutPath": "/login",
    "dashboardPath": "/dashboard"
  },
  "environment": "development"
}
```

所有 Electron 网络请求必须从统一配置读取。代码中不得继续保留旧远程域名作为业务调用地址。

Web 使用 `NEXT_PUBLIC_API_BASE_URL`，开发默认值为：

```text
http://127.0.0.1:18000
```

## 6. Web 信息架构

### 6.1 公开区域

#### 登录页

- 品牌区：Aivora 标识、产品一句话说明、本地服务状态。
- 表单区：邮箱、密码、登录、注册入口。
- 加载状态：按钮禁用并显示进行中状态。
- 错误状态：显示可读的服务错误、认证错误和网络错误。
- 登录成功后保存 Session 并进入工作台。

#### 注册页

- 邮箱、用户名、密码。
- 密码复杂度说明。
- 前端基本校验和后端错误展示。
- 注册成功后回到登录页。

### 6.2 用户区域

统一使用侧边栏和顶部状态栏：

```text
工作台
AI 任务
历史记录
模型设置
远程控制
账户设置
```

#### 工作台

- 今日任务数量。
- 运行中任务数量。
- 最近完成任务。
- 当前默认模型。
- 桌面端连接状态。
- 快速进入截图任务、任务列表和远程控制。

#### AI 任务

- 任务状态筛选：排队中、处理中、已完成、失败、已取消。
- 题型筛选。
- 创建时间和完成时间。
- 进度条和处理阶段。
- 任务详情抽屉或详情页。
- 流式答案内容、结构化答案、原始输出和警告信息。

#### 历史记录

- 搜索和筛选。
- 完成任务列表。
- 答案预览。
- 查看完整答案。
- 删除历史任务。

#### 模型设置

- 可用模型目录。
- 编程题、单选题、多选题、调试题和通用题的默认模型。
- 视觉能力标识。
- 当前服务商和接口状态。
- 保存成功、保存失败和未保存状态。

#### 远程控制

- 当前桌面设备。
- 连接码输入。
- Socket 连接状态。
- 操作按钮分组。
- 操作执行中、成功、失败和断线状态。
- 断开和重新连接。

### 6.3 管理区域

管理后台只有一个管理员角色，包含：

- 系统概览。
- 用户管理。
- AI 任务监控。
- 模型目录。
- 系统服务状态。

管理员页面必须显示加载、空数据、错误和操作成功状态，不使用静态占位数据。

## 7. 视觉系统

### 7.1 色彩

- 页面背景：浅冷灰。
- 主表面：白色。
- 主文字：深蓝灰。
- 辅助文字：中灰。
- 主操作：低饱和蓝。
- 成功：绿色。
- 警告：琥珀色。
- 错误：红色。

### 7.2 组件

建立统一组件样式：

- `Button`
- `Input`
- `Select`
- `Card`
- `Badge`
- `Progress`
- `Table`
- `EmptyState`
- `LoadingState`
- `ErrorState`
- `Sidebar`
- `Topbar`
- `Modal`
- `TaskStatus`

组件需要支持禁用、加载、错误和键盘焦点状态。

## 8. AI 任务完整链路

### 8.1 请求流程

1. Electron 采集一张或多张截图。
2. 调用 `POST /api/ai/process-screenshot`。
3. API 验证 Session、题型和图片数据。
4. 图片写入 MinIO。
5. 创建 `AITask`。
6. Redis 保存 Worker 输入。
7. 投递 Celery 任务。
8. 返回 `task_id` 和短时 `stream_token`。
9. Electron 使用 Token 连接 SSE。
10. Worker 发布进度、内容、完成或错误事件。
11. SSE 推送事件到 Electron。
12. Worker 保存 `Answer`。
13. Web 从任务详情接口读取最终结果。

### 8.2 状态

```text
queued
  → processing
  → streaming
  → completed
```

异常状态：

```text
queued / processing / streaming
  → failed
  → cancelled
```

每个状态必须有对应的 `stage`、`progress` 和用户可读错误信息。

## 9. 提示词体系

提示词从 Worker 中抽离到：

```text
backend/app/prompts/
├── base.py
├── programming.py
├── single_choice.py
├── multiple_choice.py
├── debug.py
├── universal.py
└── registry.py
```

### 9.1 基础规则

所有题型共享：

- 只依据截图内容回答。
- 无法辨认时明确说明。
- 不得编造缺失题干、选项和代码。
- 先识别题目，再分析，再输出结论。
- 多张截图必须合并理解。
- 输出适合流式展示。
- 对不确定内容增加警告。
- 代码使用 Markdown 代码块。

### 9.2 编程题

提示词要求模型：

1. 识别语言。
2. 提取题目、输入、输出和约束。
3. 列出关键边界条件。
4. 给出算法思路。
5. 给出正确性说明。
6. 给出时间和空间复杂度。
7. 给出完整可运行代码。
8. 自检变量、类型、循环、异常和边界。
9. 输出最终答案。

### 9.3 单选题

提示词要求模型：

1. 提取题干和全部选项。
2. 判断每个选项是否正确。
3. 解释排除理由。
4. 只选择一个最终选项。
5. 题目无法辨认时返回不确定警告。

### 9.4 多选题

提示词要求模型：

1. 明确按多选题处理。
2. 分别判断每个选项。
3. 输出所有正确选项。
4. 解释每个选项的判断依据。
5. 不将多选题压缩为单选结论。

### 9.5 Debug 题

提示词要求模型：

1. 识别语言和代码结构。
2. 区分语法、编译、运行和逻辑错误。
3. 标出错误位置。
4. 解释错误原因。
5. 给出最小修复方案。
6. 输出修复后的完整代码。
7. 说明修复前后的行为差异。

### 9.6 通用题

提示词要求模型：

1. OCR 提取题目。
2. 判断题型。
3. 按题目要求完成计算、推理、代码或解释。
4. 对复杂问题分步骤回答。
5. 给出明确结论和必要警告。

## 10. AI 输出协议

模型优先返回以下结构：

```json
{
  "question_type": "programming",
  "title": "题目标题",
  "analysis": "解题分析",
  "answer": "最终答案",
  "code": "完整代码",
  "complexity": "复杂度",
  "confidence": 0.92,
  "warnings": []
}
```

如果模型返回非法 JSON：

- 保存原始文本。
- 将任务标记为可展示的解析警告。
- 不丢失模型回答。
- SSE 仍发送最终内容。
- Web 页面显示“原始答案”和“解析警告”。

## 11. 测试和验收

### 11.1 后端测试

- 注册、登录和权限隔离。
- 图片 Base64 校验。
- MinIO 写入和用户权限。
- 任务创建和重复请求。
- Prompt Registry 按题型选择。
- Provider 错误和超时。
- Worker 失败状态。
- SSE Token 正确性。
- SSE 断线重连和 `Last-Event-ID`。
- 连接码过期和重复使用。

### 11.2 端到端测试

使用本地 PostgreSQL、Redis、MinIO、API 和 Worker：

1. 创建测试用户并登录。
2. 准备真实题目截图。
3. 提交截图任务。
4. 检查 MinIO 中存在输入图片。
5. 检查任务从 `queued` 进入 `processing`。
6. 检查 SSE 收到 `connected` 和 `progress`。
7. 检查 SSE 收到增量 `content`。
8. 检查 SSE 收到 `completed` 或明确 `error`。
9. 检查数据库保存答案。
10. 检查桌面端显示最终答案。
11. 检查 Web 任务详情显示最终答案。

### 11.3 桌面端验收

- 截图快捷键可以创建任务。
- 单图和多图都能处理。
- 编程题、单选题、多选题、调试题和通用题分别使用正确提示词。
- 流式答案能持续显示。
- 任务完成后显示最终结果。
- AI 失败时显示可读错误。
- SSE 断开后能恢复或明确提示。

### 11.4 构建验证

```bash
conda run -n aivora-backend python -m compileall -q backend/app
npm run typecheck
npm run build
npm run build --prefix web
```

Web 开发服务运行时，不同时执行 Web 生产构建，避免共用 `.next` 缓存导致开发服务模块不一致。

## 12. 交付标准

本次改造完成的判断标准：

- Web 不再显示初始化占位页面。
- 页面具备统一正式视觉和完整交互状态。
- Electron 不再依赖旧远程地址。
- 本地 API、SSE 和 Socket.IO 均可用。
- 至少一条真实截图能完成到答案展示。
- 失败、超时、断线和空结果都有明确表现。
- 不同题型使用不同详细提示词。
- 自动化测试和端到端验证结果可重复。
